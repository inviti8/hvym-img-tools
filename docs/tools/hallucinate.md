# hallucinate — AI-generated props and set dressing

> **SUPERSEDED by [`mesh.md`](mesh.md).** Testing showed the mesh is the
> valuable part and the texture is drawn over anyway — so dropping generative
> texturing removes the OpenRAIL-M licensing compromise, ~25 s of work, and
> 6–8 GB of weights at no cost. This file is kept as the record of *why*.

**Status (2026-08-27): DESIGN. Not implemented, and not planned.** This is the plan; nothing is
built. Grounded in the measured evaluation in
[`../benchmark/paint3d/FINDINGS.md`](../benchmark/paint3d/FINDINGS.md).

**The counterpart to [`reangle`](reangle.md), not a replacement.** Reangle moves
the artist's pixels and never redraws them. Hallucinate *does* redraw them, on
purpose, and says so in its name. Two tools, opposite contracts, one framework.

| | reangle | hallucinate |
|---|---|---|
| Texture | the artist's own pixels, front-projected | generated by a diffusion model |
| Style | preserved by construction | reinterpreted — that is the feature |
| Work | ~1.9 s | **~25 s** |
| Licensing | MIT end to end | **SD 1.5 is OpenRAIL-M** — see §6 |
| Failure mode | smear beyond ~±20° | it invents something you didn't draw |

---

## 1. Why this exists — and what it is actually for

The Paint3D evaluation killed it as a *reangle* backend for one reason: with
IP-Adapter conditioned on the artist's own drawing, it still produced a
different character — different face, proportions, Stable Diffusion's house
style. That is disqualifying when the promise is "your linework, moved".

**It is not a character tool. It is a set-dressing tool.**

An artist will not hand their protagonist to a model that reinterprets faces.
They will happily hand it a chair, a rock, a crate, a lamp — the objects a scene
needs but nobody wants to spend an afternoon drawing. Style drift on a rock costs
nothing; style drift on your lead character costs everything.

That reframing drives the rest of this document:

```
rough sketch of a chair  ──▶  hallucinate  ──▶  a chair you like
                                                      │
                                            draw on top of it
```

The output is a **starting point, not a finished asset.** That has three
consequences worth designing around:

- **The quality bar is lower than it looks.** It has to be good enough to draw
  over, not good enough to ship. Speed and plausibility beat fidelity.
- **Output should be easy to overdraw** — clean and unfussy, not busy with
  invented micro-detail that the artist then has to paint out.
- **Props are the easy case for the model.** Diffusion models are extremely good
  at chairs and rocks; they are bad at *your specific character*. The tool plays
  to the strength instead of fighting the weakness.

**One caveat, measured and worth stating up front:** the argument above is a
product judgment, not a geometric one. It was tempting to also claim props are
*easier to reconstruct and remesh*. They are not — a real chair sketch turned out
to be the **worst** case for voxel remeshing of everything tested (+60.5% silhouette,
because voxel fill bridges the gaps between the legs), and a rock fragmented worse
than the character at baseline. See
[FINDINGS.md](../benchmark/paint3d/FINDINGS.md) Follow-up 3.

What does hold: TripoSR reconstructs both props well, and quadric decimation is
safe on all of them. The remesh operating point has to be chosen per-mesh, not
per-category.

The name still does real work: **`hallucinate` tells the artist it invents.** Do
not soften it to `restyle` or `enhance`.

## 2. Contract

```
POST /tools/hallucinate     multipart/form-data
```

```python
class HallucinateInput(BaseModel):
    image: FileBytes = Field(description="Rough sketch (PNG/JPEG), any size or background")
    prompt: str = Field(
        default="",
        max_length=400,
        description="What to make it, e.g. 'a wooden chair'. Empty = infer from the sketch.",
    )
    seed: int = Field(
        default=0, ge=0, le=2**31 - 1,
        description="Fixed by default so results are reproducible and cacheable. "
                    "Change it to reroll.",
    )
    strength: float = Field(
        default=0.8, ge=0.1, le=1.0,
        description="How far from the drawing to travel. Low stays closer.",
    )
    mc_resolution: int = Field(default=256, ge=64, le=512)
```

Returns `model/gltf-binary` — **the same output shape as reangle**, so
Inkternity loads it through the identical `ArmatureModel::load_from_memory`
path and everything downstream (orbit, bake) is unchanged.

### Seed is deliberately not random

A generative tool with `seed=-1` would never hit the result cache, and "run it
again" would silently cost another 25 s of GPU. Defaulting to a fixed seed makes
the tool **reproducible and cacheable**, and makes rerolling an explicit act.
`seed` is part of the cache key via the default `cache_key_parts`, so changing
it produces a genuinely new result rather than a stale hit.

## 3. Pipeline

```
drawing ──▶ matte (isnet) ──▶ TripoSR ──▶ mesh
                                            │
                    depth-conditioned multi-view generation
                    (ControlNet depth + IP-Adapter on the drawing)
                                            │
                              back-project views ──▶ atlas ──▶ .glb
```

Geometry is **reangle's existing path** — matte, then TripoSR — plus a remesh
step. That reuse matters: it keeps one reconstruction implementation, and
TripoSR is already warm in the model cache.

The remesh is new and is measured (FINDINGS.md Follow-ups 2 and 3).
**Use quadric decimation to ~10%**: ~6× fewer UV charts for 0.93–0.98 silhouette
IoU across a character, a chair and a rock alike.

Voxel remesh buys far more chart coherence (13–50×) but is **not safe by
default** — on the chair it added 60.5% to the silhouette by bridging the gaps
between the legs. If it is ever used it must be gated on a measured silhouette
check per mesh, not chosen by category.

### Stage 2 is deliberately omitted

Paint3D's UV-space inpainting and tile refinement are **not** in this design.
Measured against our mesh they turned the atlas into formless grey mush,
because a TripoSR marching-cubes surface unwraps into 3,035 UV islands with a
median size of 2 texels. A 2D diffusion model in UV space assumes neighbouring
texels are spatially related; in that atlas they are not.

Stage 1 works because it operates in *screen* space — coherent images, then
back-projection — and never asks the model to reason about UV adjacency.

## 4. Deployment: its own image and endpoint

**Do not fold this into the reangle worker.** SD 1.5 + depth ControlNet +
IP-Adapter is roughly 6–8 GB on top of the existing 6.48 GB image. Since cold
start is already ~260 s and is dominated by image pull
([BENCHMARK.md §6b](../BENCHMARK.md)), merging them would roughly double the
wait for *every* reangle request in order to serve a tool most requests never
call.

Separate image, separate serverless endpoint, same proxy. Costs: a second
scale-to-zero worker and a second cold start. Buys: reangle's economics stay
exactly as measured.

The proxy already forwards `POST /tools/{name}` generically, so it needs a
tool→endpoint map rather than a single `RUNPOD_ENDPOINT_ID`. That is the one
piece of proxy work this requires.

### Warm leases

A lease should warm the endpoint the artist is about to use, not both. Simplest
version: `POST /warm` takes an optional `tool` field defaulting to `reangle`.
Warming both because the UI cannot tell which is coming would double the bill
for no benefit — warm time is the metered unit ([WARMING.md](../WARMING.md)).

## 5. Cost

| | reangle | hallucinate |
|---|---|---|
| GPU work | 1.9 s | ~25 s (measured, stage 1) |
| Per image | $0.00054 | **~$0.007** |

Roughly **13× reangle per call**. Still small in absolute terms, but it is no
longer a rounding error, and the numbers in BENCHMARK.md §2 apply only to
reangle. This tool needs its own cost line, not a shared one.

## 6. Licensing — needs an explicit decision

| Component | License | Commercial use |
|---|---|---|
| Paint3D code | Apache-2.0 | yes |
| Paint3D UV-position ControlNet | Apache-2.0 | yes |
| **Stable Diffusion 1.5** | **CreativeML OpenRAIL-M** | **yes, with behavioural restrictions** |
| ControlNet (lllyasviel) | Apache-2.0 | yes |

**This would be the first thing we ship that is not permissively licensed.**
OpenRAIL-M is far better than CC-BY-NC — it permits commercial use, which is why
Wonder3D was rejected and this is not — but it is not OSI-permissive, and it
attaches use restrictions that propagate to anyone we distribute the model to.

Consequences to accept deliberately:

- The README's "**MIT end to end**" line stops being true for the suite and must
  become per-tool.
- OpenRAIL-M's behavioural restrictions bind our users too, so they belong in
  the client-facing docs, not just here.
- The [AGENTS.md](../../AGENTS.md) convention — *document each tool's model
  licenses; CC-BY-NC is demo-only, never a shipped default* — is satisfied by
  documenting this, but the spirit of "sovereign, permissive" is bent.

**Alternative worth pricing before committing:** an SD-derived base under a more
permissive license, or a fully-permissive alternative, would keep the suite
clean. Not researched yet.

## 7. What the artist sees

- **Name it honestly in the UI.** "Hallucinate" or "Reimagine" — never
  "Enhance", which implies the original is being improved rather than replaced.
- **Show the input beside the output.** The whole risk is the artist not
  realising how far it travelled.
- **Never default it on**, and never silently substitute it when reangle fails.
- **Expect ~25 s plus cold start**, so the same indeterminate-spinner guidance as
  reangle applies ([CLIENT.md](../CLIENT.md)), with a longer expectation.

## 8. Open questions

1. **Does the *texture* hold up on props?** The geometry half is now measured
   (Follow-up 3) and the answer was "not as assumed". What remains untested is
   the part the tool actually depends on: whether depth-conditioned generation
   produces a *better chair* than the artist's rough sketch. Diffusion models
   are good at chairs, so this is plausible — but it is now the last unverified
   link in the chain, and the prop meshes to test it on already exist.
2. **Should `prompt` be exposed at all?** A free-text prompt is a wide surface —
   it invites results far from the drawing and is the main path to content we
   would rather not generate. A fixed internal prompt plus `strength` is
   narrower and more predictable. Leaning toward exposing it, but it is a real
   choice.
3. ~~**Would a remesh/decimation pass help?**~~ **Answered: yes.** Decimating
   to 10% of faces gives 5.9× fewer UV charts while keeping 97.6% of the
   silhouette — free enough that reangle should probably adopt it regardless.
   Voxel remesh reaches 50× fewer charts but inflates the silhouette by bridging
   gaps, which is not correctable by an offset. See FINDINGS.md Follow-up 2.
4. **Is there a permissively-licensed base model** that would keep §6 clean?

## 9. What is already proven

From [FINDINGS.md](../benchmark/paint3d/FINDINGS.md), on a rented 4090:

- kaolin 0.17.0 installs on sm_89 with torch 2.4.1+cu124 — the project's pinned
  cu113 stack is unnecessary, so any modern GPU tier works.
- Stage 1 runs on our TripoSR mesh and produces a coherent textured result in
  ~25 s.
- Setup needs three fixes: `--ignore-installed blinker`,
  `huggingface_hub==0.20.3`, `numpy<2`, and `accelerate==0.25.0`.
- Stage 2 does not work on our topology and is excluded above.
- **If a generative fill is ever added on top of the projection, composite it** —
  keep the artist's pixels verbatim outside the mask and take the model only
  inside. Measured: that gives exactly 0.00 drift, where tuning
  `denoising_strength` from 0.3 to 1.0 changed drift by 0.1%.
